# Supabase Backend Configuration & Database Setup

This guide documents the database architecture, schema migrations, stored procedures (RPCs), and Row Level Security (RLS) policies required to deploy the **Nammalvar** backend on Supabase.

---

## 1. Prerequisites

- A **Supabase** account ([supabase.com](https://supabase.com)) with an active project.
- **Supabase CLI** (optional, recommended for automated local migrations) or web-based SQL Editor.
- PostgreSQL 15+ compatible engine.

---

## 2. Environment Configuration

To link your Flutter terminal to your Supabase instance, supply your **Project URL** and **Publishable Anonymous Key**:

### Method A: Compile-Time Variables (Recommended for CI/CD)
```bash
flutter run \
  --dart-define=SUPABASE_URL="https://your-project.supabase.co" \
  --dart-define=SUPABASE_ANON_KEY="your-anon-publishable-key"
```

### Method B: Environment Template (`.env.example`)
Duplicate `.env.example` to `.env`:
```ini
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_ANON_KEY=your-anon-publishable-key
```

> [!CAUTION]
> Never embed your Supabase `service_role` key in Flutter client code or commit `.env` files to version control. The client only requires the `anon` publishable key; database security is enforced by Row Level Security (RLS).

## 4. Database Schema Specification

### Relational Tables (12 Core Entities)

1. **`public.profiles`**: Store personnel profiles linked to `auth.users(id)` via Foreign Key with `user_role` (`admin` or `seller`).
2. **`public.categories`**: Hierarchical category tree supporting self-referencing subcategories (`parent_id`).
3. **`public.products`**: Catalog inventory containing selling prices, purchase cost rates, current physical stock, unit measures (`kg`, `litre`, `piece`, etc.), and minimum threshold levels.
4. **`public.sales`**: Sale invoice headers with auto-incrementing serial invoice numbers (`sale_number`), authenticated seller attribution, and payment method flags (`cash`, `upi`, `other`).
5. **`public.sale_items`**: Immutable line-item snapshots recording historical item names, units, and rates at the exact moment of transaction.
6. **`public.stock_movements`**: Immutable audit ledger logging every stock alteration (`opening_stock`, `purchase`, `sale`, `sale_cancel`, `adjustment`) along with user attribution and reason.
7. **`public.price_history`**: Audit trail generated by database triggers whenever a product's selling or cost price changes.
8. **`public.suppliers`**: Organic farmers and artisanal vendor directory.
9. **`public.purchases`**: Inward stock procurement records.
10. **`public.purchase_items`**: Line items for inward shipments.
11. **`public.expenses`**: Daily operational overhead expenditures categorized into transport, packaging, rent, electricity, maintenance, and wages.
12. **`public.activity_logs`**: System audit log recording security and management events.

## 5. Concurrency-Safe Stored Procedures (RPCs)

To guarantee ACID compliance and eliminate client-side race conditions, critical state changes are executed via PostgreSQL stored procedures:

### `process_sale(p_payment_method payment_method, p_items JSONB)`
- Derives seller identity directly from `auth.uid()`.
- Validates active profile status.
- Acquires pessimistic row-level write locks (`SELECT ... FOR UPDATE`) on all cart items.
- Verifies sufficient stock; raises an exception if requested quantity exceeds availability.
- Atomically reduces `current_stock`, inserts `sales` header, inserts `sale_items`, creates `stock_movements` audit ledger rows, and writes an `activity_logs` entry.

### `cancel_sale(p_sale_id UUID, p_reason TEXT)`
- Enforces admin authorization via `public.is_admin()`.
- Requires a mandatory cancellation reason.
- Locks the sale record (`FOR UPDATE`).
- Restores original item quantities back to `products.current_stock`.
- Writes reversing entries to `stock_movements` with movement type `sale_cancel`.
- Updates sale status to `cancelled` and records cancelling admin and timestamp.

### `receive_stock(...)`
- Admin-restricted procedure to record supplier invoices and increment inventory.

### `adjust_stock(...)`
- Admin-restricted procedure for physical cycle-count adjustments with mandatory reason logging.

## 6. Row Level Security (RLS) Policy Matrix

RLS is enabled on all 12 tables. The policy matrix is summarized below:

| Table | SELECT | INSERT | UPDATE | DELETE |
|---|---|---|---|---|
| `profiles` | All authenticated users | Admin or Self (`auth.uid() = id`) | Admin or Self (`auth.uid() = id`) | Admin only |
| `categories` | All authenticated users | Admin only | Admin only | Admin only |
| `products` | All authenticated users | Admin only | Admin only | Admin only |
| `sales` | Admin or Invoice Seller (`seller_id = auth.uid()`) | Via authenticated `process_sale` RPC | Admin only | Restricted |
| `sale_items` | Admin or Item Seller | Via authenticated `process_sale` RPC | Restricted | Restricted |
| `stock_movements` | All authenticated users | Handled by RPCs | Restricted | Restricted |
| `price_history` | Admin only | Trigger-managed | Restricted | Restricted |
| `suppliers` | Admin only | Admin only | Admin only | Admin only |
| `purchases` | Admin only | Admin only | Admin only | Admin only |
| `purchase_items` | Admin only | Admin only | Admin only | Admin only |
| `expenses` | Admin only | Admin only | Admin only | Admin only |
| `activity_logs` | Admin only | System / RPC | Restricted | Restricted |

## 7. Realtime Publication

To enable real-time updates across multiple terminals, the following tables are published to the Supabase Realtime replication stream:
```sql
ALTER PUBLICATION supabase_realtime ADD TABLE public.products;
ALTER PUBLICATION supabase_realtime ADD TABLE public.sales;
ALTER PUBLICATION supabase_realtime ADD TABLE public.categories;
ALTER PUBLICATION supabase_realtime ADD TABLE public.stock_movements;
ALTER PUBLICATION supabase_realtime ADD TABLE public.expenses;
```
